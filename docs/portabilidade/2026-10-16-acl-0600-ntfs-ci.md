## Contexto

O Go no Windows ignora os 9 bits POSIX de permissão: `os.Chmod` e `os.WriteFile(…, 0o600)` só
alternam o bit `READONLY` do atributo. A ACL real de um arquivo é herdada do diretório pai no
momento em que `os.CreateTemp` cria o arquivo temporário; o `Rename` que segue não altera a ACL.

Os 5 sítios que pedem `0o600` são:

| arquivo | sítio |
|---|---|
| `internal/identity/identity.go:93` | identity.json |
| `internal/integrations/manifest.go:92` | integrations-manifest.json |
| `internal/integrations/render.go:730` | render output |
| `internal/thirdparty/quarantine.go:114` | quarantine record |
| `internal/thirdparty/provenance.go:155` | provenance record |

Todos usam `atomicWrite` / `pathguard.GuardedWrite`. Os diretórios pai são criados com
`MkdirAll(…, 0o700)` — que também é inerte além do bit `READONLY`.

Esta medição (W2a) visa responder: quem além de dono/SYSTEM/Administrators tem Write nos
arquivos criados pelo binário real em cada cadeia de herança?

## ACL das raízes (fonte de herança)

### `C:\`
```
icacls C:\:
  S-1-15-3-65536-...:(S,RD,X,RA)            ← App Container SID
  NT AUTHORITY\Authenticated Users:(AD)      ← CreateFiles na raiz
  NT AUTHORITY\Authenticated Users:(OI)(CI)(IO)(M)  ← Modify herdado por filhos
  NT AUTHORITY\SYSTEM:(OI)(CI)(F)
  BUILTIN\Administrators:(OI)(CI)(F)
  BUILTIN\Users:(OI)(CI)(RX)
  Mandatory Label\High Mandatory Level:(OI)(NP)(IO)(NW)
```

- `(OI)(CI)(IO)(M)` = ObjectInherit + ContainerInherit + InheritOnly + Modify.
- Significa: **qualquer arquivo ou diretório criado sob `C:\` (direta ou indiretamente)
  herda Modify para `NT AUTHORITY\Authenticated Users`**.
- Autenticação no Windows inclui todos os usuários logados localmente, incluindo usuários de
  domínio e usuários de rede.

### `D:\`
```
icacls D:\:
  BUILTIN\Administrators:(OI)(CI)(F)
  NT AUTHORITY\SYSTEM:(OI)(CI)(F)
  CREATOR OWNER:(OI)(CI)(IO)(F)
  BUILTIN\Users:(OI)(CI)(RX)
  BUILTIN\Users:(CI)(AD)       ← AppendData/AddSubdirectory
  BUILTIN\Users:(CI)(IO)(WD)   ← herda só para contêineres (CI sem OI): subpastas, não arquivos
  Everyone:(RX)
```

- `BUILTIN\Users:(CI)(IO)(WD)` = ContainerInherit + InheritOnly + WriteData.
- Significa: **subpastas** de `D:\` herdam WriteData (= criar arquivo) para `BUILTIN\Users`; **arquivos não herdam** esse ACE (sem `OI`). O `icacls` bruto de `identity.json` neste braço mostra só `BUILTIN\Users:(I)(RX)`.

## O que não foi medido

1. **`integrations-manifest.json`** (manifest.go:92): `trackfw agents install --scope project`
   requer `--targets` em modo não-TTY; o braço root-c não criou este arquivo. Pelo mecanismo
   de herança confirmado (arquivos sob `C:\p17-proj\` herdam de `C:\`), o manifesto teria a
   mesma ACL que o identity.json medido acima.

2. **Perfil não-admin:** o runner é administrador. Em máquina de usuário padrão, `C:\Users\<user>\.trackfw\`
   pode ter ACL diferente (tipicamente mais restritiva). O braço root-c representa o pior caso
   documentado, pois herda da raiz `C:\`.

3. **ARM64:** não medido; apenas x64.

4. **Proveniência e quarentena** (provenance.go:155, quarantine.go:114): escritas em
   `<projeto>\.trackfw\thirdparty-provenance.json` e `<projeto>\.trackfw\thirdparty-quarantine\<hash>.json`.
   Se o projeto for criado diretamente sob `C:\`, os arquivos herdariam Modify para Authenticated
   Users — o mesmo padrão do braço root-c. Segurança: um usuário local poderia sobrescrever a
   proveniência para fazer uma instalação adulterada passar como aprovada.

## Limites da medição

- Runner elevado (admin); ACL de `C:\Users\runneradmin` é mais permissiva que a de um perfil
  padrão (o administrador criou o diretório, não o usuário que criaria em produção).
- A herança de `C:\` com `Authenticated Users:(OI)(CI)(IO)(M)` é configuração padrão do
  Windows — verificada e documentada, não específica do runner.
- `D:\a\_temp` é `RUNNER_TEMP` deste runner; a letra de drive e as ACLs de `D:\` podem variar
  entre imagens de runner.
